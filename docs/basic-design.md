# トークリア 基本設計書

更新日：2026年10月18日（日本時間）

[要件定義書](requirements.md) に基づき、現行版の画面・データ・処理・実行環境をまとめる。制作情報と起動方法は [README](../README.md) を参照。

## 1. 画面設計

### 入室画面

- 入力：表示名、自分が読む言語（日本語・英語）、参加時のルームID。
- 操作：「部屋を作る」または「部屋に参加」。作成時はアプリがルームIDを自動発行する。
- 表示言語：右上の「日本語 / English」で切り替える。日本語を既定とし、選択をブラウザに保存する。
- 読む言語：表示言語の切り替え時に同じ言語を自動選択する。その後は読む言語だけを手動変更でき、選択を保存する。
- 言語を切り替えても、表示名・ルームID・作成／参加の選択を保持する。
- アカウント登録・ログイン画面は設けない。
- 主見出しは「慣れた言語で話そう！」。実際のチャットと共通の吹き出し、名前・時刻、原文表示を使って3発言の会話例を載せる。会話例に利用者の履歴は使用しない。

### チャット画面

- 表示：ルームID、参加者、会話履歴、翻訳文、翻訳状態、送信者の表示名と日時。
- 操作：文章の入力・送信、「原文を見る」、退出。
- 自分の発言は原文、相手の発言は選択した言語で表示する。翻訳された発言では原文も確認できる。
- 翻訳の準備中・ダウンロード中・失敗時には状況を表示する。利用できない間も原文で会話を続けられる。
- サイドバーと会話の境界をドラッグ、または左右キーで操作すると幅を変更できる。ダブルクリックで既定幅264pxへ戻す。
- サイドバーの幅はブラウザに保存する。画面が狭い場合は、会話領域を確保する範囲に制限する。
- 同名の参加者には識別子の一部を添える。
- 入室中はその参加情報の読む言語を維持する。言語を変更する場合は退出して選び直す。
- タブの再読み込みでは参加を再開する。明示的な退出後の再入室は新しい参加者として扱う。

### 共通の表示・操作

- 正式名称は日本語「トークリア」、英語「Talklear」。ブラウザのタイトルは「トークリア｜自動翻訳チャット」／「Talklear | Automatic Translation Chat」。
- 不正なルームIDや空欄等の入力エラーは、その場で理由を伝える。
- 見出し・ルームID・長い文章は必要に応じて折り返す。
- 縦スクロールバーは非表示にし、履歴・メンバー欄・長いホーム画面のスクロール操作は維持する。
- メッセージの編集・削除用の画面は設けない。

## 2. データ設計

PostgreSQLに部屋・参加者・メッセージを保存する。画面とAPIはJSONで通信する。実際の定義は [schema.sql](../src/main/resources/schema.sql) を参照。

| テーブル | 主な項目 | 関係・役割 |
|---|---|---|
| `chat_rooms` | UUID、12文字のルームID、作成日時 | 参加者とメッセージを部屋単位で分ける。 |
| `chat_participants` | UUID、部屋ID、表示名、読む言語、トークンのハッシュ、最終通信日時、退出日時 | 部屋に所属し、発言者と参加状態を管理する。 |
| `chat_messages` | 連番ID、部屋ID、参加者ID、送信識別子、原文、入力言語、送信日時 | 部屋と発言者に関連付けて履歴を保存する。 |

- 日時はタイムゾーン付きで保存する。
- 参加者にランダムな参加トークンを発行し、DBにはハッシュ値を保存する。APIでは部屋とトークンを照合する。
- 最終通信から45秒間通信がない参加者を参加中一覧から外す。明示的な退出ではトークンを無効化し、発言者情報は履歴用に残す。
- 入力言語はChromeのLanguageDetector APIで判定する。利用不可・短文で不明確な場合は文字種で補う。読む言語とは分けて保存し、判定できない場合は `und` とする。
- 翻訳結果はブラウザのメモリに一時保持する。原文と読む言語が同じ場合や、文字を含まない文章では翻訳を省略する。
- 送信識別子を部屋・参加者と組み合わせて一意にし、同じ送信の再試行で重複保存しない。
- 同じ部屋の送信時は、DBの部屋行をロックして保存順序をそろえる。IDの採番後、確定前の発言を新着取得で飛ばさないようにする。
- 退出後も履歴を残す。自動削除・部屋の有効期限・保存期間は未設定。

## 3. 画面遷移・会話処理

1. 部屋を作る人：入室画面 → 表示名・読む言語を選択 → 部屋を作成 → チャット画面でルームIDを確認 → 友人に伝える。
2. 参加する人：入室画面 → 表示名・読む言語・ルームIDを入力 → 参加 → チャット画面。
3. 会話：入力 → 送信 → サーバーで保存 → 同じ部屋の参加者が取得 → 必要に応じて翻訳 → 表示。
4. 退出・再入室：チャットから退出 → 入室画面 → 同じルームIDで参加 → 過去の会話を確認。

### 新着・履歴の取得

- 通常時は2秒ごとに新着の追加分を取得する。
- 入室直後は最近100件を表示し、以前の会話を追加取得できる。
- 新着の取得位置は新着取得の応答だけで更新する。自分の送信結果や過去履歴の取得では進めない。
- 発言はID順に表示し、同じ発言を重複して追加しない。送信結果が先に届いても、後から取得した他の発言を正しい位置へ挿入する。

### 失敗時の扱い

- 通信・保存に失敗した場合は入力文を保持し、理由と再試行の手段を表示する。
- 翻訳機能が利用不可、データのダウンロード失敗、翻訳失敗の場合も原文を表示する。
- 未送信の文章がある状態で退出する場合は確認を出す。
- 別の部屋へ参加するときは、前の部屋の取得状態をリセットする。

## 4. 使用技術・実行環境

| 技術 | 役割 |
|---|---|
| Java 21 / Spring Boot 3.5.16 / Spring JDBC | API、入力検証、入退室、会話履歴の保存・取得。 |
| HTML / CSS / JavaScript | 入室画面・チャット画面の表示と操作。 |
| PostgreSQL 18.6 | 部屋・参加者・会話履歴の保存。 |
| Chrome Translator API / LanguageDetector API | 端末内での翻訳と入力言語の判定。 |
| Maven 3.9 | Javaの依存関係管理・ビルド。 |
| JUnit / Node.js標準テスト | サーバー、会話取得、翻訳処理、Docker経由の動作の検証。 |
| Docker / Docker Compose | ローカルのアプリ・DBの起動。 |
| GitHub Actions | 自動テスト、JavaScriptの構文チェック、コンテナのビルド。 |

### アプリと翻訳の構成

- Spring Bootの1つのアプリから静的な画面とAPIを提供する。
- 原文の送受信・保存にはサーバーとPostgreSQLを使う。翻訳処理のみ、利用者のPC内で行う。
- 翻訳サービスの契約・APIキー・カード登録は不要。初回はChromeの翻訳用データをダウンロードする。
- PC版Chromeを自動翻訳の対応環境とする。スマートフォンの自動翻訳は現行版に含めない。

### ローカル環境

- 標準の起動はDocker Compose。アプリは `Dockerfile.vercel`、DBは公式PostgreSQLイメージを使う。
- DBのヘルスチェックが成功してからアプリを起動する。
- PC側の公開先は `127.0.0.1:8080` が標準で変更可能。DBのポートはPCへ公開せず、アプリから `db:5432` で接続する。
- `CHAT_PUBLIC_ORIGIN` は `http://localhost:PC側ポート` とする。
- DBは名前付きボリューム `translate-chat-local_postgres-data` に保存し、PostgreSQL 18の保存先 `/var/lib/postgresql` へマウントする。
- 初回生成したDBパスワードとポートはGit管理外の `.local/docker.env` に保存する。停止時は保存用ボリュームを削除しない。
- ボリュームが存在して設定ファイルが失われた場合は、パスワードを再生成せず、復元を案内して起動を止める。
- 非Docker版ではツールを `.tools/`、DBを `.local/postgres/` に保存する。Docker版とは保存先を分け、自動移行しない。

### クラウド環境

Vercel HobbyとNeon Freeで公開。アプリはローカルと同じDockerファイルからビルドし、DBはNeonへ接続する。Neon連携の `PG*` 環境変数から、証明書とホスト名を検証するTLS接続を構成する。`CHAT_DB_*` の明示設定も維持する。本番URLはログイン不要、プレビューはVercel認証で保護する。設定は [公開手順](deployment.md) を参照。

## 5. 実装工程と検証

### 実装の段階

| 段階 | 実装した内容 | 確認すること |
|---|---|---|
| 1 | 入室・チャットの2画面、部屋作成、ID発行、参加、原文での会話 | 複数の画面で同じ部屋に入り、送受信・退出できるか。 |
| 2 | PostgreSQLへの保存、履歴取得、再入室 | 再入室・再起動後に履歴が残り、部屋が混ざらないか。 |
| 3 | 翻訳、原文表示、準備中・失敗時の表示 | 日英双方向の表示と、翻訳できない場合の会話継続。 |
| 4 | 画面調整、Docker対応、全体検証 | 入室から再入室までの操作、狭い画面での表示、保存領域の維持。 |

### リスクと対策

| リスク | 対策・残課題 |
|---|---|
| 翻訳の利用不可・品質不足 | 状態と原文を表示し、再試行できるようにする。利用者による品質評価は今後の課題。 |
| 履歴の混入・不正アクセス | 部屋と参加トークンを照合し、別室のデータを取得できないことを検証する。 |
| ルームIDの漏えい | ランダムな12文字を発行し、連続操作を制限する。ルームIDを知る人の参加は防げないため、失効方法・期限は残課題。 |
| 同時送信・通信の順序違い | 部屋行のロック、新着取得位置の分離、ID順の表示で取りこぼしを防ぐ。 |
| 通信・保存の失敗 | 入力を保持し、送信識別子によって再試行時の重複保存を防ぐ。 |
| コンテナの再作成 | DBを名前付きボリュームへ保存する。設定ファイル紛失時に既存DBを別パスワードで初期化しない。 |
| 無料公開環境の上限 | 利用条件・利用状況・保存の継続性を確認し、公開URLで検証する。 |

## 7. UI方針

- 白系の背景、濃い緑のサイドバー・ボタン、薄い緑の自分の発言を用いる。
- 入室画面は会話例とフォーム、チャット画面は参加者のサイドバー・会話・入力欄で構成する。
- 画面の狭さや拡大表示に合わせて折り返しと領域の高さを調整する。
- 送信・翻訳の状態やエラーを文章で示し、キーボードでも主要な操作を行えるようにする。
- 言語を切り替えても操作の意味と表示内容をそろえる。
