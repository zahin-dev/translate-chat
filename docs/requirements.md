# トークリア 要件定義書

更新日：2026年10月18日（日本時間）  
制作開始日：2026年9月1日  
制作人数：3名（チーム制作）

本書は、トークリアの目的・対象ユーザー・現行版の機能と制約をまとめる。画面・処理・データの詳細は [基本設計書](basic-design.md)、起動方法と検証結果は [README](../README.md) を参照。

## 1. アプリの概要・目的

- 正式名称：日本語「トークリア」、英語「Talklear」。日本語の表示タイトルは「トークリア｜自動翻訳チャット」。Talk（会話）＋Clear（明確に伝わる）を組み合わせた名称。
- 目的：異なる言語を話す友人同士が、外部の翻訳アプリへ文章をコピーする手間なく、日常的な雑談をできるようにする。
- 概要：チャットと自動翻訳を統合したWebアプリ。各参加者が読む言語を選び、その言語で相手のメッセージを読む。
- 現行版の範囲：PC上での部屋の作成・参加、グループ会話、日英の自動翻訳、会話履歴の保存。

## 2. 対象ユーザー

- 対象：日本語話者と英語話者。
- 利用シーン：海外の友人との日常的な雑談。1対1と複数人の会話に対応する。
- 利用方法：参加者それぞれがこのWebアプリを開き、同じルームIDで参加する。
- 自動翻訳の対応環境：PC版Chrome。翻訳を利用できない環境でも原文で会話できる。
- 将来の方向性：対応言語を増やす。現行版の翻訳と言語選択は日本語・英語に限る。

## 3. 基本機能（現行版）

| 機能 | 利用者ができること |
|---|---|
| 部屋の作成 | 部屋を作ると、ルームID（招待ID）が自動発行される。 |
| 部屋への参加 | 友人から伝えられたルームIDを入力して参加する。 |
| 表示名の入力 | アカウント登録をせず、表示名を入力して参加する。 |
| 画面の表示言語の切り替え | ホーム画面で日本語・英語を切り替えられる。 |
| サイドバーの幅調整 | チャット画面でルームID・メンバーを表示するサイドバーの幅を変更できる。 |
| メッセージを読む言語の選択 | 入室時に日本語・英語から選ぶ。ホームで表示言語を切り替えた際は、読む言語も同じ言語を自動選択する。その後の手動変更も可能。 |
| テキストチャット | 2人でも複数人でも、同じ部屋でメッセージを送受信する。 |
| 入退室 | 部屋に参加・退出でき、参加者を画面で確認できる。 |
| 自動翻訳・原文表示 | 相手のメッセージは選んだ言語で表示し、「原文を見る」で元の文章を確認する。自分の発言は原文で表示する。 |
| 会話履歴 | 退出後も履歴を残し、同じIDで再入室すると以前の会話を読める。IDを共有された参加者も過去の会話を読める。 |
| 翻訳できない場合の継続 | 翻訳の準備中・失敗等の状態を伝え、原文での送受信を続けられる。 |
| 2画面構成 | 入室画面とチャット画面を使う。 |

## 4. 将来の拡張候補

以下は現行版には含めない。追加する際に必要性と優先順位を検討する。

- 日本語・英語以外の翻訳。
- スマートフォンでの自動翻訳。
- メッセージの編集・削除。
- 音声・画像送信、通知。

## 5. データ項目（何を記録するか）

現在の保存情報を以下に示す。実際のDB定義は [schema.sql](../src/main/resources/schema.sql) を参照。

| 分類 | 記録する主な項目 | 目的 |
|---|---|---|
| 部屋 | 内部ID、ルームID、作成日時 | 会話を部屋ごとに区別し、IDで参加できるようにする。 |
| 参加者 | 内部ID、所属する部屋、表示名、読む言語、参加トークンのハッシュ、参加状態 | 発言者を識別し、部屋へのアクセスと参加中一覧を管理する。 |
| メッセージ | 内部ID、部屋、送信者、原文、入力言語、送信日時、送信識別子 | 発言を保存し、再入室時に履歴を表示する。再送時の重複保存を防ぐ。 |

- 入力言語はChromeの言語判定と文字種で判定する。翻訳結果はDBには保存せず、ブラウザのメモリに一時保持する。
- タブの再読み込みでは参加情報を復元する。明示的な退出後に再入室すると、新しい参加者として扱う。
- 会話の保存期間・削除方法、部屋の有効期限は未決定。現行版に自動削除機能はない。

## 6. 制約条件

### 技術・実行環境

- 画面：HTML / CSS / JavaScript。
- サーバー：Java / Spring Boot。
- データ保存：PostgreSQL。
- 標準のローカル環境：Docker ComposeでアプリとDBを起動する。会話履歴はコンテナと別の保存領域に残す。
- Dockerを使わない起動方法も用意する。Docker版と保存先を分け、データは自動移行しない。
- 自動テスト：JUnit、Node.js標準テスト、Docker経由の結合テスト。
- 翻訳：PC版ChromeのTranslator APIを使い、端末内で処理する。翻訳サービスのAPIキーやカード登録は不要。
- 翻訳用データの初回ダウンロードにはインターネット接続が必要。チャットの送受信・履歴保存にはアプリのサーバーを使う。
- ソースはGitHubで公開済み。クラウド版はVercel HobbyとNeon Freeで準備中。公開URLでの動作確認は未完了。手順は [公開手順](deployment.md) を参照。

### セキュリティ・利用上の制約

- 表示名は30文字、メッセージは2,000文字以内。履歴は最近100件から表示し、以前の会話を追加取得できる。
- アカウント登録はないため、表示名による本人確認は行わない。
- ルームIDを知る人は参加し、過去の履歴も読める。IDは会話相手に限って共有する。
- 部屋と参加トークンの照合、入力検証、連続操作の制限、送信元の検証を行う。
- 短文・日英混在・固有名詞では、言語判定や訳文が不自然になる場合がある。原文の確認手段を残す。
- 無料プランには上限がある。無制限利用や常時稼働の保証は対象外とする。

## 7. 完成・公開の確認条件

ローカル版は以下の操作を確認済み。最新の検証件数と結果は [README](../README.md#テスト動作確認) に記載する。

- 複数のブラウザ画面で同じ部屋に参加し、日本語・英語の双方から会話できる。
- ルームIDの共有、表示名・言語選択、参加・退出までの一連の操作ができる。
- 選択した言語で相手のメッセージを読み、必要時に原文も確認できる。
- 再入室後に以前の会話を読める。アプリ・DBのコンテナ再作成後も保存状態を維持する。
- 翻訳の準備中や失敗時も、原文による送受信を続けられる。
- 別の部屋の会話が混ざらず、不正なルームIDや空欄入力等を適切に扱う。

クラウドの公開完了には、HTTPSの公開URLで上記の操作と保存状態を確認する必要がある。利用者による翻訳品質の評価は今後の課題とする。

## 8. 設計判断と残課題

| 論点 | 採用方針・理由 | 代替方式との違い・制約 |
|---|---|---|
| 専用チャット | 会話と翻訳を同じ画面で完結させる。 | 既存SNSの連携方式と異なり、双方がアプリを開く必要がある。 |
| 複数人の会話 | 友人同士のグループで使えるよう、部屋単位で参加者と発言を管理する。 | 1対1限定の構成より、参加状態と部屋間の分離の検証が必要になる。 |
| アカウント登録なし | 表示名とルームIDで参加でき、利用開始の手順を減らす。 | アカウント方式と異なり、人物の継続的な本人確認やID漏えい時のアクセス管理に制約がある。 |
| Java / Spring Boot | API、入力検証、トランザクションによる保存処理をまとめて構成する。 | 画面も同じアプリから配信する。React等によるフロントエンドの分離は現行版では行わない。 |
| PostgreSQL | 部屋・参加者・発言を関連付け、整合性を保って履歴を保存する。 | ファイル保存よりDBの準備が必要だが、同時送信や検索を扱いやすい。 |
| Docker | アプリとDBの実行環境をそろえ、起動・停止の手順を共通化する。 | Docker Desktopが必要。非Docker版の保存先とは別管理になる。 |
| 端末内の翻訳 | 翻訳サービスへの従量課金を避け、翻訳処理のために本文を外部APIへ送らずに済む。 | 外部API方式より対応ブラウザ・端末の制約が大きい。現行版は日英に限定する。 |
| 翻訳失敗時の原文表示 | 翻訳の失敗で会話全体を止めない。 | 訳文を必須にする方式と異なり、原文確認と再試行を利用者が選べる。 |

主な残課題は、会話の保存期間・削除方法、部屋の有効期限、部屋数・人数の上限、翻訳品質の利用者評価、クラウド公開の完了。

仕様変更時は、本書と [基本設計書](basic-design.md) の画面・データ・処理・検証項目、および [README](../README.md) の機能・制約を照合する。
